# huh: working notes

Living log of decisions, gotchas and what's left. Newest decisions at the bottom of each section.

## Layout
```
src/Huh.App          WinUI 3 tray app + bubble (assembly "Huh", namespace "Huh")
src/Huh.Core         UI-free: detection, dialog model, decoding, provenance, AI, privacy, actions
tools/Huh.TestHarness  raises error / non-error dialogs on demand (console, comctl32 v6 manifest)
tools/Huh.Probe      headless host for Core detection; JSONL log + harness scoring + verified screenshots
tools/icons          make-icons.ps1 (huh.ico, huh-paused.ico, huh-256.png)
docs/                reports/ (M1-M4 numbers), images/ (README screenshots), demo-script.md
tests/Huh.Tests      xUnit v3 (Microsoft.Testing.Platform runner)
```

## Build & run
- Build: `dotnet build Huh.slnx -c Debug -p:Platform=x64`
- Tests: `dotnet test --project tests/Huh.Tests`
- App:   `src/Huh.App/bin/x64/Debug/net10.0-windows10.0.26100.0/win-x64/Huh.exe`

## Decisions
- **.NET 10** (`net10.0-windows10.0.26100.0` for the app, `net10.0-windows` elsewhere). .NET 8 support ends 2026-11-10.
- **Unpackaged + self-contained Windows App SDK** (`WindowsPackageType=None`, `WindowsAppSDKSelfContained=true`) so the app
  can be launched/killed/screenshotted from the CLI. `EnableMsixTooling` stays on (needed for resources.pri). MSIX is optional (M6).
- Project renamed to **Huh.App**, but `AssemblyName=Huh` / `RootNamespace=Huh` to avoid a `Huh.App.App` namespace/type clash.
- Platforms: x64 + ARM64 (x86 dropped). Libraries are AnyCPU.
- Removed the template's `systemAIModels` capability: no NPU on the target machine (i7-1355U), so Windows AI APIs are unavailable.
- **Central package management** (`Directory.Packages.props`).
- **UI Automation via raw COM generated by CsWin32**, not FlaUI: FlaUI depends on tlbimp interop (built-in COM), which is
  disabled under trimming (Release publish trims). Raw COM also gives explicit control of UIA threading.
- **Tray icon via raw Shell_NotifyIcon** (H.NotifyIcon.WinUI is pre-release only).
- **Gemini default model `gemini-3.8-flash`, fallback `gemini-3.5-flash-lite`** (free tier per Google's pricing page, checked 2026-11-05).
  `gemini-2.5-flash` is deprecated (rerouted 2026-12-01). Free-tier data IS used by Google to improve products.
- **AI is opt-in**: nothing goes to Gemini until the user accepts on the first-run screen (which explains free-tier data use).
  Deterministic info (codes, source program, signature) works without AI.
- **Re-run as admin**: exe path only, never arguments. Blocked for unsigned binaries; override shows a red warning with the path + "unsigned".
- AI-chosen actions carry parameters that are validated (ms-settings from a fixed list, folders must exist locally, search query built by huh).
  Dialog text is untrusted input (prompt-injection vector).

### M1 detection design
- `DialogMonitor` (Core) = WinEvent hooks (own thread + message loop) + UIA WindowOpened (desktop subtree) feeding ONE MTA
  worker thread. Hook callbacks only filter/forward; UIA reads happen on the worker (never on a UI/STA thread).
- Cheap pre-filter before any UIA call: class `#32770`, known dialog classes (`OperationStatusWindow`), DIALOGSTART/ALERT,
  UIA IsDialog, or an error-ish title. Everything else is skipped.
- Content is read **only via UIA** (one `FindAllBuildCache` round trip). Win32 is used for metadata only: class, caption,
  pid, and the MessageBox icon's *resource id* (`STM_GETICON` + `GetIconInfoEx`; no pixels).
- Classifier is pure and unit-tested: error words / error codes / error icon > question phrasing > warning > info.
- De-dupe: same hwnd, or same (pid, title, message), within 3 s. Own process always ignored.
- UIA timeouts set to 1.5 s (IUIAutomation2) so a hung app can't stall the worker; reads retry 3x with backoff.
- Verified with `Huh.Probe score`: 28/28 error dialogs, 0/6 false positives, three consecutive runs; p50 ~167 ms.
  Idle cost ~0.9% of one core, 37 MB. Report: `docs/reports/m1-detection.md`.
- Caveat: the text rules were written before the first run, but the harness and the rules come from the same author.
  Real-world precision will be lower; the per-app exclusion list (M6) is the safety valve.

### M2 bubble design
- Dev display: one 14" 1920x1200 panel at **125% (120 DPI)**, work area 1920x1140. Mixed-DPI placement is covered by unit
  tests on fake monitor geometry (no second monitor available).
- `BubblePlacer` (Core, pure): bubble size in DIPs, converted with the DPI of the monitor the bubble *lands on*; prefers
  right > left > below > above > overlap-the-corner; slides along the dialog edge to stay in the work area; when it spills
  onto a neighbouring monitor it's pushed fully onto it (away from the dialog, never over it).
- `WindowFollower` (Core): out-of-context hooks scoped to the dialog's pid/tid for LOCATIONCHANGE, SHOW/HIDE and
  MINIMIZESTART/END, plus global FOREGROUND. Created on the UI thread (WinUI pumps Win32 messages, so callbacks arrive there).
- `BubbleWindow` (App): OverlappedPresenter with border but no title bar (keeps the native shadow + rounded corners),
  `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`, `IsShownInSwitchers=false`, shown with `SW_SHOWNOACTIVATE` (never `Activate()`).
  Height is content-driven (XAML measure at 340 DIP wide), re-placed on size change.
- Z-order: directly above its dialog (not topmost) unless the dialog itself is topmost. An unrelated window covering the
  dialog also covers the bubble.
- `AlwaysActiveAcrylic`: custom SystemBackdrop with `IsInputActive=true` and higher tint/luminosity opacity than the default
  (the stock acrylic was unreadable over busy content).
- App has no main window: `DispatcherShutdownMode.OnExplicitShutdown`. Diagnostics log at `%LOCALAPPDATA%\huh\logs\huh.log`
  (events only, never dialog text). `HUH_THEME=Light|Dark` forces a theme for testing.
- Verified with `Huh.Probe bubble` (46 checks over 5 dialog types: focus never stolen, styles, placement == placer to the pixel
  at 5 positions + a simulated drag, z-order incl. a covering window, minimize/restore of the owner, close). 46/46 in 5
  consecutive runs, dark and light theme. Report: `docs/reports/m2-bubble.md`. Screenshots stay in `artifacts/` (they show the
  dev's user path in the bubble, so they're not committed).

### M3 deterministic decoding (no AI)
- `ErrorCodeDecoder`: finds 0x-hex (8 digits, not inside 16-digit pointers), bare WSH-style hex (`800A03EA`), .NET negative
  HRESULTs, and decimals after cue words ("error 1619"); decimals Windows doesn't know are dropped. Classifies NTSTATUS
  (0xC..., N-bit clear) vs HRESULT (facility 7 => inner Win32) vs Win32 (<0x10000). Text from FormatMessage (system table,
  ntdll for NTSTATUS, wininet/winhttp for 12xxx), cleaned (`{Title}` headers stripped, `%hs`/`%1` -> "…"). Small curated
  symbolic-name table (`KnownCodes`); Windows has no API for names.
- `Authenticode`: WinVerifyTrust offline (`WTD_REVOKE_NONE` + cache-only URL retrieval, no UI), signer from the leaf cert.
  Catalog fallback via CryptCATAdmin. "Embedded vs catalog" decided from the PE certificate table.
- `SourceAnalyzer` badges: signed by X / unsigned (publisher "claims to be" CompanyName) / invalid / Store app (publisher from
  the package's AppxManifest.xml; OS verified it at install) / Windows itself (csrss etc., "about X.exe" from the hard-error
  title) / web page in <browser> (origin from "x.com says").
- Browser JS alerts are drawn INSIDE the browser window (no HWND). Trigger: EVENT_SYSTEM_ALERT from Chrome_RenderWidgetHostHWND.
  A dedicated MTA thread does a shallow BFS of the browser's own UI (never into Document/web content) for
  `JavaScriptTabModalDialogViewViews` or IsDialog, retrying ~2 s (the first UIA query switches on Chromium accessibility).
  Bubble anchors to the alert's rect, translated as the browser moves; closure detected by polling the element (400 ms).
- Facts are built on the monitor worker thread (WinVerifyTrust off the UI thread); typically 1-60 ms, first call ~200 ms.
- Real-world run (Run dialog, empty .msi, Notepad save to C:\, System32 copy): all four bubbles correct after the fixes below.
  Screenshots via `Huh.Probe snap`: verifies dialog + bubble are topmost (WindowFromPoint) and masks every other pixel.

### M4 AI explanations (opt-in)
- Consent: `ConsentWindow` on first run (and from the bubble's "Explain this with AI" link). Settings in
  `%LOCALAPPDATA%\huh\settings.json`; AI is off until accepted. Key: GEMINI_API_KEY env var, else DPAPI file
  `%LOCALAPPDATA%\huh\gemini.key` (pasted on the consent screen). The key is only ever placed in the `x-goog-api-key` header.
- Pipeline (`AiExplainService`): consent gate -> `Redactor` (profile path -> %USERPROFILE%, other profiles, user name,
  computer name, e-mails) -> `Prompt` (untrusted text fenced in <dialog_data> with tags neutralised; huh facts in
  <verified_facts>) -> cache (SHA-256 of prompt, 30 days, `%LOCALAPPDATA%\huh\cache\ai`) -> `GeminiExplainer` ->
  `Explanation.Sanitized` -> `InjectionDetector` -> `FixActions.Validate`.
- `GeminiExplainer`: generateContent, `responseJsonSchema`, `thinkingLevel: LOW`, 8 s per model; falls back to the next model
  on 429 / 404 / 503 / timeout. Every failure is an `AiOutcome` (NoKey, Quota, Busy, Timeout, Network, Auth, ...); the
  bubble shows one line and keeps the M3 info.
- Action rules: allowlist only; settings pages from a fixed key list; folders must exist on a local fixed/removable drive
  (no UNC, variables, files); re-run as admin only for signed normal programs, exe path only, never arguments, always
  confirmed; web pages: copy text only; search queries built by huh. Injection detected => no action + caution banner.
- Dev: `HUH_AI_FAKE=1` (canned answer) / `HUH_AI_FAKE=quota` (simulated 429): no network, AI "on" in memory only, real
  consent untouched. Bubble checks run with HUH_AI_FAKE=1 so they don't spend quota.
- Results: `docs/reports/m4-ai.md` (live latency 2.1-4.1 s on the primary; cache hit 38 ms).

### M5 fix actions (code done; on-screen checks pending, see "Left")
- Flow: suggested-fix button (AI) or always-available links (Copy / Search / Run as admin…) -> inline confirmation that shows
  exactly what will happen (`Confirmations.For`: page name + URI, full folder path, query, program + full path + publisher +
  "Arguments: none") -> `FixActionRunner` -> `IActionLauncher` (`WinAppLauncher` in the app). Copy runs without confirmation.
- Unsigned re-run: never suggested by the AI; user-initiated only. Red panel (path + "UNSIGNED"), checkbox
  "I understand this program is unsigned" must be ticked before the button enables; the runner refuses without the ack.
- Windows shell/system processes are never re-run (explorer, csrss, dllhost, rundll32, svchost, conhost, powershell, cmd,
  msiexec, ... and anything under %SystemRoot%). The decision carries a hint pointing at the dialog's own button
  ("Use the dialog's own "Continue" button"); the prompt tells the model "part of Windows: yes" and to suggest that instead.
- Click-time re-checks (TOCTOU): settings key still on the list, folder still a folder, exe path unchanged, signature and
  signer unchanged (re-verified with WinVerifyTrust), eligibility re-evaluated. UAC "No" (Win32 1223) => "Cancelled".
- Launcher guards: OpenUri only `ms-settings:`/`https:`; folders open via `explorer.exe <folder>` (ArgumentList, no shell
  verb on the path); runas sets WorkingDirectory only, never Arguments, owner = bubble HWND. Search = Bing with a query built
  by huh from redacted facts.
- Changing the system prompt changes the cache key, so earlier cached answers are not reused (next live run = fresh calls).
- Tests: `ActionTests` (every action's validation, system-process denylist, confirmations, runner incl. forged actions,
  folder->file swap, unsigned ack, signature change, UAC cancel, injection cases). 207 tests total.

### M6 polish (2026-11-07)
- **Tray** (`Core/Windowing/TrayIcon.cs`): raw Shell_NotifyIcon, NOTIFYICON_VERSION_4, hand-written blittable P/Invoke +
  `[UnmanagedCallersOnly]` window proc. Hidden WS_POPUP window (not message-only: those miss the "TaskbarCreated" broadcast
  sent when Explorer restarts). Menu: status line, Pause, AI explanations, Start with Windows, Settings (default), Quit.
  Left click = Settings. Dark native menus via undocumented uxtheme ordinals 135/136 (harmless if missing). Paused icon variant.
- **Single instance**: named mutex `Local\huh-<hash of data dir>`; a second launch posts WM_APP+2 to the tray window ("open
  Settings") and exits. Keyed by data dir so a HUH_DATA_DIR test instance can run beside the real one.
- **Pause** is in memory only (restart = watching again). Paused => detections ignored, open bubbles closed, grey icon.
- **Start with Windows**: HKCU Run value `huh` = `"<exe>"` (no admin). Task Manager's StartupApproved\Run "disabled" counts as
  off; enabling from huh clears it. Off by default. If the registered exe no longer exists (zip moved), startup repoints it;
  a registered exe that still exists is left alone (could be the copy the user wants).
- **Settings window** (Mica, content extended into the title bar): watch/pause, startup, AI on/off (turning on needs the
  consent screen unless accepted before and a key exists), provider (Gemini; Ollama listed disabled as "coming later"),
  model + fallback (editable, validated `^[a-z0-9][a-z0-9.\-]*$`, max 64: the name goes into the URL path), API key
  replace/remove (DPAPI), excluded apps (picked from recently seen apps), privacy section, about.
- **Exclusions** key = exe name; for csrss hard errors the program the error is *about*; for web pages the browser.

- **Privacy preview** (`RequestPreview`): URL + headers (key shown as a placeholder) + pretty JSON body built by the same
  `Prompt.Build` + `GeminiExplainer.BuildBody` as a real request; unit test asserts JsonNode.DeepEquals with what the fake
  HTTP handler received. Sources: a sample dialog using the user's real profile path (shows redaction) or the last dialog.
- **First run**: welcome step (3 lines + tray hint) in `ConsentWindow`, then the AI question. Users who decided before M6
  count as having seen the welcome. Consent copy: free-tier note moved to the top of the list, "change it any time: tray ›
  Settings", a "Get a free key" link. `AiConsentAt` is now kept after turning AI off (re-enabling needs no new consent).
- **Pre-warm**: at startup, facts pipeline on a sample (WinVerifyTrust embedded + catalog, FormatMessage, prompt) on a pool
  thread, then one bubble for `SampleFacts` built, DWM-cloaked, moved off-screen, shown, rendered for 3 frames, closed.
  Release build, 6 runs each (screen locked): first bubble's first frame median ~375 ms with pre-warm vs ~670 ms without;
  later bubbles ~285 ms. Outliers ~770 ms in 2/6 pre-warmed runs (one: the dialog's own app was slow, 570 ms detection; one
  unexplained, 470 ms between show and first frame).
- **Motion** (`Motion.cs`): entrance = 14 DIP slide from the dialog's side + fade (220/160 ms, cubic ease-out, compositor
  properties only), AI panel / confirmation fade-in, 120 ms fade-out on close. All skipped when `UISettings.AnimationsEnabled`

- **Release**: `dotnet publish -c Release -p:Platform=x64 -p:PublishProfile=win-x64` (self-contained, trimmed, R2R).
  Only `Microsoft.WindowsAppSDK.WinUI` + `.Runtime` are referenced (the metapackage added ONNX Runtime, DirectML, Search,
  Widgets: 156 MB -> 95 MB, zip 39 MB). No PDBs in Release; scanned all 308 files for user name / e-mail / computer name.
- **Icons**: `tools/icons/make-icons.ps1` (System.Drawing) writes huh.ico, huh-paused.ico (PNG entries 16-256) and huh-256.png.
- **Screenshots** for the README in `docs/images/`: reused M3-M5 crops; the Windows user name in the two path screenshots replaced by
  `<you>` drawn in Cascadia Mono on the exact character cells. Dropped a crop that had 1-2 px slivers of the desktop.

## Gotchas
- `SupportedOSPlatformVersion` can't be set globally: `net10.0-windows` has TargetPlatformVersion 7.0 (NETSDK1135).
- .NET 10 SDK: `dotnet test` needs `"test": {"runner": "Microsoft.Testing.Platform"}` in global.json for xUnit v3; use `dotnet test --project ...`.
- TaskDialog needs a Common Controls v6 manifest dependency (harness has one).
- Mica/Acrylic render the inactive fallback in a never-activated window, so force `IsInputActive=true` (M2).
- `Window.Activate()` steals focus, so show the bubble with `SW_SHOWNOACTIVATE` (M2).
- CsWin32: `CsWin32RunAsBuildTask=true` + `allowMarshaling:true` gives `[GeneratedComInterface]` COM (trim-safe).
  `allowMarshaling:false` gives raw vtable structs instead. Some shell structs (SHELLEXECUTEINFOW) need a concrete PlatformTarget.
- **UIA does not expose the icon type** of a MessageBox (unnamed Static image) or TaskDialog ("MainInstructionIcon").
  `STM_GETICON` handles don't match `LoadIcon(NULL, IDI_*)` (MessageBox loads DPI-scaled copies), but `GetIconInfoEx` resource ids
  do: imageres #98 error, #84 warning, #81 info, #99 question (module name is a datafile handle string); csrss hard-error boxes use
  user32 #32513..32516. TaskDialog icon type is still unknown, so TaskDialogs rely on text cues.
- `EVENT_SYSTEM_SOUND` never fired for MessageBox on this machine, so it's not usable as a severity signal.
- TaskDialog: UIA hides `DirectUIHWND`; identify it by AutomationIds (`MainInstruction`, `ContentText`, `CommandButton_*`).
- Caption buttons can have AutomationIds like `Minimize-Restore`; filter by prefix + empty ClassName.
- Explorer text contains U+200E bidi marks; strip Unicode Format chars.
- msiexec's dialog times out (`0x80131505`) on the first UIA read while the process starts up, so reads must retry.
- Shell "File In Use" is an `OperationStatusWindow` (not #32770) and only appears if another process holds the lock and the
  IFileOperation has an owner window.
- The csrss hard-error box ("code execution cannot proceed") IS readable from medium IL.
- **Invisible resize borders**: SetWindowPos sizes the *outer* rect; a bordered window's visible frame is inset (8 px at
  125%). Compensate with GetWindowRect vs DWMWA_EXTENDED_FRAME_BOUNDS.
- **EVENT_SYSTEM_FOREGROUND arrives before the new foreground window is raised**, so re-stack again ~120 ms later.
- **Minimizing a dialog's owner HIDES the dialog** (no destroy). Treating HIDE as close killed the bubble for good (content
  de-dupe then blocked re-detection). Only EVENT_OBJECT_DESTROY means closed; the bubble follows SHOW/HIDE itself.
- A dialog can be destroyed before the UI thread gets to its bubble (cold XAML start): check the dialog still exists before
  creating/showing a bubble.
- XAML type-info generator tries to `new` public property types of a Window: keep `DialogInfo` properties internal.
- A process started by the probe inherits the probe's stdout; if the probe dies without killing it, `| grep` never sees EOF.
- TaskDialogs without a Cancel button ignore WM_CLOSE.
- First launch after a rebuild can take ~12 s to reach OnLaunched (most likely Defender scanning new binaries); normally ~0.7 s.
  First bubble after start ~0.6-1.7 s (XAML cold start); later bubbles 85-270 ms.
- **Windows 11 dialogs use U+2019 in "don’t"/"can’t"**: normalise quotes before matching (missed the Notepad permission box).
- Notepad's permission box is a TaskDialog whose first line is the path; headline skips path-only lines.
- On this build csrss.exe/kernel32.dll carry embedded signatures even though Get-AuthenticodeSignature reports "Catalog";
  System32\notepad.exe is catalog-only. dotnet.exe's signer is ".NET".
- File-mode WinVerifyTrust already validates catalog-signed files on current Windows.
- `PACKAGE_ID` is arch-specific in CsWin32 (AnyCPU can't generate it): read AppxManifest.xml instead.
- Chromium doesn't raise UIA WindowOpened for tab-modal JS dialogs; a full-page UIA FindFirst can take seconds and once
  stalled the single detection worker (fixed: separate thread + shallow BFS + 2 s rate limit per window).
- Background processes can't take focus (foreground lock) and the user's windows can cover test dialogs: screenshots must be
  verified and masked, or they capture the user's screen. Never automate keystrokes while the user is typing.
- `sed` with `\n`/`\u` in replacements mangles C# escapes; use the editor for those lines.
- Gemini docs now lead with the Interactions API; `generateContent` is still current. JSON output: `responseMimeType` +
  `responseJsonSchema`; thinking: `thinkingConfig.thinkingLevel` (Gemini 3+ only).
- `gemini-3.8-flash` returned 503 UNAVAILABLE ("high demand") for ~10 min on 2026-11-06 while flash-lite worked: 503 must
  fall back, not just 429. The model metadata GET (free) is a good first check that the key and model are fine.
- **A model will obey prompt injection** (flash-lite did): the validator + deterministic detector are the real defence,
  never the system prompt.
- PowerShell passes `$null` as "" to string P/Invoke parameters (FindWindow(null, title) needs [NullString]::Value).
- Fixture JSON with nested JSON strings: generate with a serializer, never hand-escape (raw control chars, `\D`).
- Harness `run` scenarios that spawn helpers (rundll32/regsvr32/msiexec) report the helper's process; the probe matches by name.
- **PrintWindow returns black for WinUI 3 content** (composited); screenshots of huh's windows must come from the screen,
  after verifying nothing covers them.
- **CsWinRT needs `partial` on classes deriving from WinRT types** (our `SystemBackdrop` subclass): without it the trimmed
  Release build throws InvalidCastException in `set_SystemBackdrop`. Debug builds work, so test the published build.
- **ILLink writes its output PDB's full path (`obj\...\linked\Huh.pdb`) into the binary even with PathMap**: the user name
  leaks into release DLLs. Release uses `DebugType=none`.
- The Microsoft.WindowsAppSDK metapackage pulls ~60 MB of AI/ML runtimes into a self-contained build; reference components.
- First launch of freshly built/extracted binaries takes 11-40 s to reach OnLaunched (Defender scanning ~300 files); the
  second launch of the Release build starts in ~270 ms.
- PowerShell: `Get-ChildItem <dir> -File -Exclude x` without `-Recurse` matches nothing (a "clean" scan that scanned no files).
  The tool's guard blocks any command containing `Remove-Item` plus a C:\ path, and also misreads robocopy's `/E` as a path.

## UIPI (verified 2026-11-06)
Elevated harness (`Start-Process -Verb RunAs`) + non-elevated probe: the dialog IS detected (WinEvents cross integrity levels),
caption and UIA `IsDialog` are readable, but the UIA subtree is empty and `STM_GETICON` is blocked.
`OpenProcessToken` still works on a same-user elevated process, so we see `Elevation=Elevated` and set `BlockedByUipi=true`.
Retries are skipped for elevated/AccessDenied targets (they'd only add ~1.5 s). huh can't close or click such dialogs either.
